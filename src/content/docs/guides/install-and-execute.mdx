# Install and execute

There are two different stories in the current Tapid project:

- The implemented story is deterministic installation and root-script execution against a validated local fixture or supported registry path.
- The planned story is an evidence-first flow for resolving a package, applying policy, and then installing or executing it.

Keeping those stories separate prevents a design proposal from being mistaken for a working command.

## Implemented: replay a validated project

The current consumer path uses an existing `tapid.lock` and verified store content. It does not resolve metadata or download archives.

```bash
tapid install --offline --frozen --project-dir ./example
tapid run --project-dir ./example test -- --runInBand
```

The repository fixture verifies that installation creates managed `node_modules`, dependency lifecycle scripts do not run, root-script arguments are forwarded, and the child exit code is returned.

## Planned: add a project dependency

This is not implemented in the current CLI:

```shell
# Proposed package command, not accepted by the current CLI yet.
tapid install is-char
```

The current CLI responds with `unexpected argument 'is-char' found` because positional package resolution is not implemented yet. The intended flow is to resolve `is-char` to an exact version, registry object, and artifact digest, present available evidence, apply the project's policy, update the dependency graph and lockfile, and materialize the artifact only after the decision permits it.

## Planned: run a package tool

This is also a proposal, not a working command today:

```shell
# Proposed command, not a working command today.
tapid x release-helper@1.8.2 -- --check
```

The `--` boundary would separate Tapid's arguments from the tool's arguments. The intended design is to resolve and inspect the exact tool artifact before execution. No Tapid agent runner, sandbox, or capability enforcement service exists today.

## The boundary that matters

A successful local fixture replay proves a narrow implementation path. It does not prove that Tapid can assess arbitrary npm packages, detect malware, verify publisher provenance, sandbox scripts, or enforce runtime permissions. Those capabilities remain planned, incomplete, or explicitly outside the current implementation.

Read [Commands](/docs/commands/) for the implemented CLI surface, then continue to [Evidence and policy](/docs/concepts/evidence-and-policy/) to understand the planned decision model.
