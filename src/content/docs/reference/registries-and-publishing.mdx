# Registries and publishing

A registry is both a package source and a trust boundary. The package name and version are not enough if two registries can provide different package objects for the same request.

## What the client supports today

The current Tapid client supports a local JSON registry fixture for tests and air-gapped development. It does not yet provide private-registry authentication, publishing, or a complete public npm compatibility surface.

The fixture path is intentionally narrow:

```bash
tapid install --registry-fixture ./fixture.json --project-dir ./example
```

Do not treat this as registry authentication or a production mirror feature.

## Routing and credentials

Future registry routing should make the source explicit. A private scope should not fall through to a public registry because a configuration entry is missing. Registry credentials should stay within the boundary that needs them and should never be silently sent to another origin.

Those rules connect registry configuration to [package identity](/docs/concepts/package-identity/): the registry object is part of the identity that a lockfile and later replay must reproduce.

## Publishing and release history

A future publishing flow should record publisher identity, provenance where available, and release changes that affect an artifact, metadata, or declared capability. A corrected release, a compromised publisher, and an artifact that must no longer be accepted by unattended systems may require different policy outcomes.

The final revocation, namespace governance, and independent verification rules remain open design work. Tapid does not currently provide a registry service, provenance verifier, package discovery service, or publishing command.
